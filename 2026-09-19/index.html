TL;DR

RAFT 的主要增益不是「多建一張圖」，而是把 query 對到歷史案件裡相同的調查狀態，再把完整處理軌跡交回 agent。

Entry-level state match drives Case Hit; graph expansion is explicitly optional evidence diversification.
§1 pp.1–2; §4.2 p.5; Appendix C.5 p.14
WHY STATIC RAG MISSES THE JOB

Troubleshooting is a moving target

  • 0%: only a symptom or error code — retrieval should find productive initial directions.
  • Later: logs, hypotheses, and observations arrive — the relevant historical evidence changes.
  • A useful result needs both the matched moment and the coherent diagnosis-to-resolution trajectory.
  • Raw cases also mix noise, non-actionable closures, and potentially sensitive customer content.
The retrieval unit must preserve investigation progression, not merely document similarity.
§3 p.3
BASELINE FAILURE MODE

Static chunks create a reconstruction tax

Case-level / chunk RAG
  • Ranks raw passages from long, heterogeneous tickets.
  • Returns isolated evidence; agent must reassemble the parent case.
  • More returned chunks consume context and restrict how many cases can be examined.
Entity GraphRAG
  • Builds offline entity/relation structure.
  • Does not explicitly encode the progression of one investigation.
  • Adds graph-construction cost and binds retrieval to an entity-centric representation.
§1 pp.1–2; §3 p.3
PAPER CONTRIBUTIONS

A two-level retrieval memory for support cases

  1. Structured trajectory: timeline entries + root cause + resolution + entities + review.
  2. Entry-level hybrid search: retrieve the state matching the active case, then promote distinct parent cases.
  3. Optional case graph: expand from good seeds toward related root causes / remedies.
  4. Open evaluation: 826 synthetic Windows Server cases plus human-grounded Apache Jira transfer evidence.
§1 p.2; §4 pp.3–5; §5 pp.5–7
SYSTEM OVERVIEW

Offline distillation; online state-aware retrieval

Fig. 1 p.4
METHOD 1 / OFFLINE EXTRACTION

Represent a case as an editable investigation trajectory

  • Workers process ordered emails, notes, logs, and other artifacts in bounded batches, carrying accumulated case state forward.
  • A timeline entry starts only at a meaningful state transition: symptom, changed hypothesis, confirmed root cause, or verified resolution.
  • A reviewer checks source evidence and revision history, then produces a structured assessment such as actionability.
  • The compact trajectory records what changed in the investigation, not every conversational turn.
Ki ≪ Ti: semantic state entries compress many raw turns without losing the useful transitions.
§4.1 pp.3–4; Appendix B.2 pp.11–12
METHOD 1 / SHARED WORKSPACE

Carry state forward, not the whole conversation

Source evidence stays selectively queryable; the compact updated state and handoff notes survive the next pass.
Fig. 2 p.12; Appendix B.2 pp.11–12
METHOD 2 / INDEX

Two levels of memory, two different jobs

Entry-level index
  • Embed every timeline entry.
  • Use metadata, entities, and reviewer assessments as filters.
  • Find the historical state closest to the active investigation.
Optional case graph G
  • Link cases by configurable fields; experiments use root cause + resolution.
  • Hybrid semantic + BM25 pair scoring, fused with RRF.
  • Used after seed retrieval to seek complementary evidence.
§4.1 pp.4–5
METHOD 3 / ONLINE RETRIEVAL

Rank entries; promote parent cases under a budget

rank(q, entry) = RRF(semantic(q, entry), BM25(q, entry))
  1. Apply an optional case filter; score all remaining timeline entries.
  2. Sort entries and greedily accept only the first hit from each parent case.
  3. Stop at n distinct cases or context budget B.
  4. Return each parent trajectory plus the triggering anchor entry.
The agent sees which state matched — not just an opaque case ID or disconnected chunk.
Algorithm 1 p.5; §4.2 p.5
AGENT LOOP

The retrieval query evolves with the investigation

Direct path
  • q1: symptom → opening historical states
  • q2: hypothesis/logs → intermediate states
  • q3: narrow evidence → later states / remediation
Expansion path
  • Agent chooses whether to expand from seed cases.
  • Graph neighbors can share a cause or remedy despite different symptoms.
  • Expansion reserves a fixed slot rather than flooding the context.
Fig. 1 p.4; §4.2 p.5; Appendix C.5 p.14
EVALUATION PROTOCOL

Test retrieval at three moments, under one budget

8267 categories6,000 tokens
  • Synthetic corpus: Microsoft Learn Windows Server troubleshooting documents, held out one case per root-cause group.
  • Queries reveal prefixes at 0%, 30%, 60% of case progress.
  • All methods share text-embedding-3-large, gpt-5.2 indexing, gpt-5.4 evaluation, and no metadata filtering.
  • Case-level methods retrieve at most five distinct cases; Fast-GraphRAG receives only the token cap.

LIMITS

Good retrieval evidence is not an end-to-end agent result

  • Main evaluation is synthetic and moderate scale; production corpora are larger and longer.
  • Apache Jira has 30 audited duplicate groups and no confidence intervals; it is directional transfer evidence.
  • No evaluation of diagnosis correctness, actual resolution success, or engineer productivity.
  • RAFT pays an offline LLM extraction cost; end-to-end economics depend on query volume and downstream context consumption.
Limitations p.8; Appendix C.7 p.15; Appendix D p.15
ENGINEERING INTERPRETATION

Three design lessons for agent memory

  1. Index transitions, not only artifacts. A ticket is useful because its diagnosis changed over time.
  2. Return an anchor with its trajectory. The anchor explains relevance; the parent case exposes the resolution path.
  3. Separate precision from exploration. Direct entry retrieval produces good seeds; graph expansion spends a bounded slot on diverse evidence.
This is a retrieval design for evolving work states, not a generic “add GraphRAG” recipe.
§3 p.3; §4 pp.3–5; Appendix C.5 p.14
