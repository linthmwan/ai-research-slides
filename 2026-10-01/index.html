TokenWeave: Efficient Compute-Communication Overlap for Distributed LLM Inference

Raja Gond · Nipun Kwatra · Ramachandran Ramjee
Microsoft Research India
MLSys 2026 OralarXiv:2505.11329v5

把 AllReduce、RMSNorm 與 GPU wave 排程一起重做；讓 tensor-parallel LLM serving 從 1K tokens 開始也能有效 overlap。

Source: TokenWeave, MLSys 2026 · Abstract p.1 · arXiv:2505.11329
One-line thesis

不是把通信藏起來而已；先把 RMSNorm 的冗餘計算與 HBM traffic拿掉，再讓通信不搶走 compute 的 SM。

結果：在 8xH100 上，latency 最多 1.28x、實際 workload throughput 最多 1.19x。
Abstract p.1; §4.3 p.8; §5 pp.9–12

Bottleneck

Tensor parallelism 的通信仍在 critical path

  • 每個 Transformer block 有兩次 AllReduce；即使是 NVLink 的 8xH100 DGX，通信仍佔 end-to-end latency 9–23%。
  • RMSNorm 再佔 4–9%；把它當小 operator 忽略，會錯過真正可融合的路徑。
  • Interactive serving 不會總有 8K+ tokens；vLLM 0.8.5 的 default chunk size 是 2K。
Fig.1 p.1; §1 pp.1–2
Why prior overlap misses serving

切小 kernel 才能 overlap，但 GPU 不喜歡太小的 kernel

Prior approach

  • 把 computation 切成 tiles / sub-tasks。
  • 一部分通信與另一部分計算並行。
  • 常需拆 AllReduce 成 ReduceScatter + AllGather。

Failure mode

  • 小工作量造成 wave quantization。
  • RS + AG 可能比一個 AllReduce 多出顯著成本。
  • 小 batch 時，切分損失大過被藏掉的通信。
重點不是「能不能 overlap」，而是「切分後還保不保持 kernel efficiency」。
§1 p.2; §3 pp.5–6; Fig.4 p.4
Design target

讓 overlap 適用於 1K-token serving batch，而不是只在大 batch 微基準裡好看。

TokenWeave 的答案：兩路 token pipeline + wave-aware split + fused AllReduce–RMSNorm。
§1 pp.2–3
Safety valve

不是每次都硬做 overlap

低 token 數先拿 fusion 的確定收益；足夠大才啟用 split + overlap。
Fig.3 p.3; §4 p.6
Method overview

兩個 token split，織出兩條 CUDA streams

Compute stream

  • 處理 split 0 / split 1 的 attention 與 FFN。
  • Chunked attention 保留 prefix-to-suffix dependency。

Communication stream

  • 對另一 split 跑 fused AllReduce + RMSNorm。
  • 以 stream wait 做輕量同步。
split 0 compute || split 1 (AllReduce -> RMSNorm) ; then swap
§4 pp.6–7; Fig.7 p.6
Scheduling constraint

「均分」不是 Smart-splitting

  • H100 有 132 SMs；300 CTAs 原本是 2 full waves + 1 partial wave。
  • 若粗暴均分為兩個 150-CTA kernels，每個都變成 full + partial，合計從 3 waves 變成 4。
  • Smart-splitting 選 132 + 168 CTAs，讓兩邊 waves 的總數不超過原始 workload。
它優化的是 split 後的 total wave count，不是 token 數的表面公平。
§4.1.1 p.7
Wave intuition

先守住 occupancy，才有可靠的 overlap window

Fig.9 reports Smart-split reduces split overhead particularly at short sequence lengths.

Fig.8 p.6; Fig.9 p.7; §4.1.1 p.7
Reordering

把 RMSNorm 移到 ReduceScatter 後、AllGather 前

  • ReduceScatter 完成後，每張 GPU 已擁有 1/N 的完整 token embeddings。
  • RMSNorm 是 token-level operation；在 local shard 做它，避免每張 GPU 對完整 tensor 重複算一次。
  • 但只有 reordering 不夠：RS + AG 的額外 HBM traffic 會抵消這個好處。
AllReduce + RMSNorm -> ReduceScatter -> local RMSNorm -> AllGather
§4.2 p.8
Kernel path

Fused kernel 把值留在 registers，不走多餘 HBM

  1. NVSHARP ReduceScatter：switch fabric 對 local 1/N shard 做 reduction。
  2. In-register RMSNorm：reduced values 立刻做 variance / normalization；residual addition 同時融合。
  3. Direct Multimem AllGather：normalized values 直接寫入 multicast address，交給 switch 分發。
省掉 initial HBM read 與額外 write，同時消除 full-tensor RMSNorm redundancy。

Hardware fit

為 overlap 保留 SMs，而不是讓通信吃掉 SM pool

  • 作者的 fused path 在 8xH100 上僅用 2–8 SMs。
  • 相比 prior work 的 16–20+ SMs，compute stream 有更大機會真的並行。
Fig.5 p.4; §4.3 p.8
Mechanism crown

TokenWeave 成功的真因：先縮資源 footprint，再排重疊。

RMSNorm reordering 消掉 N 倍重複；fusion 消 HBM 往返；Multimem 留 SM；Smart-splitting 不新增 waves。
因此它甚至能比「移除所有通信」的 counterfactual baseline 更快——後者沒有修 RMSNorm。
§4.2–4.3 p.8; Fig.2 p.2; Fig.13 p.10

End-to-end throughput

Dense models 在 reported workloads 約 1.19x；Mixtral 的收益較低，和其較低通信 overhead 一致。

Latency

Dense models 從 1K tokens 起維持增益

Dense 8xH100 runs: 1.16x–1.28x improvement from 1K onward; Mixtral has weaker / short-length caveats.

Fig.13 p.10; §5.2.2 p.11
Single-layer comparison

TileLink 要到 4K+ 才開始贏；TokenWeave 在 1K 已有 1.20x

TileLink

  • Small sequences: net overhead in the reported comparison.
  • Improvement begins at >=4K tokens and saturates around 1.2x.
  • Overlap constrained to GEMM contexts.

TokenWeave

  • 1K tokens: 1.20x single-layer latency speedup.
  • Up to 1.35x in the reported single-layer figure.
  • Fused communication + RMSNorm overlaps with compute.
§5.2.3 p.11; Fig.14 p.10
Ablation

先有 fusion 的確定收益，full overlap 再往上疊

  • Fused-only: 1.04x–1.09x across models，來自少掉 redundant RMSNorm 與 HBM accesses。
  • Full TokenWeave: 再疊加 compute–communication overlap。
Fig.16 p.12; §5.2.5 p.12
Ablation interpretation

Smart-splitting 主要修的是「不穩定」

  • Equal split 的 gain 會跟 exact sequence length 一起 jitter。
  • 根因是 naïve split 的 wave quantization 在某些 lengths 顯著、某些 lengths 幾乎不顯著。
  • Smart-splitting 幾乎消除這種 jitter，讓收益在 sequence-length sweep 裡更一致。
效率系統要看的不只 peak speedup；曲線是否平滑，決定 production scheduler 能不能信它。
§5.2.5 p.12; Fig.17 p.12
Boundary conditions

這不是無條件的 acceleration

  • 硬體依賴：fused implementation 以 Hopper / Blackwell / future NVIDIA 的 NVSHARP + Multimem 為前提。
  • Mixtral-8x22B 的 1K / 2K full overlap 有 net overhead；此時系統回退到 fused-only。
  • TileLink / NanoFlow 沒有直接整合 vLLM，cross-system comparison 的設計受限。
作者的正確取捨是 selective enable，而不是把一個 kernel strategy 強塞所有 request。
§2.2 p.4; §5.2.2 p.11; §5.1 p.10
Engineering takeaway

對 inference optimizer 而言，最值得問的不是「還能不能多開一條 stream」，而是：現在每一個 SM 與 HBM access 到底在做什麼。

TokenWeave 把這個問題落到可部署的 vLLM path：重排、fusion、resource reservation、再 scheduling。
§4 pp.6–8
Appendix · highlighted source

Wave-aware 的原文定義

“The splitting is carefully chosen to be wave-aware, ensuring that the total number of waves executed in kernels of the two splits is not more than the number of waves if there were a single non-split kernel.”

切分刻意讓兩個子 kernel 的 wave 總數不超過未切分 kernel 的 wave 數；它直接針對 split 的隱性 occupancy 損失。

§1 p.2
Appendix · highlighted source

Fusion 為何快的原文描述

“We then perform RMSNorm computation immediately on this reduced portion available in the SM registers without using the HBM.”

ReduceScatter 後的 shard 直接在 SM registers 做 RMSNorm，不先讀寫 HBM；這使 fused kernel 不只是「把三個操作包在一起」。

§4.3 p.8
Appendix · result caveat

Mixtral 的反例讓 selective enable 變成必要

“In MoE, the tokens for MLP computation get split across the experts ... even TokenWeave’s coarse splitting into two subtasks can result in non-trivial overheads.”

MoE 的 expert split 會使小 request 的 FFN memory-bound；即使只是兩個 coarse splits 也可能虧，因此只有 fused kernel 的 fallback 不是附帶功能。
