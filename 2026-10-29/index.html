DynaFlow: Transparent and Flexible Intra-Device Parallelism via Programmable Operator Scheduling

Yi Pan, Yile Gu, Jinbin Luo, Yibo Wu, Ziren Wang, Hongtao Zhang, Ziyi Xu, Shengkai Lin, Baris Kasikci, Stephanie Wang · UW / SJTU
MLSys 2026Announced 2026-05-20（回溯 17 天）

Venue: Proceedings of the 9th MLSys Conference, Bellevue, 2026（PDF p.1 頁尾）· arXiv 2605.21603 · 回溯原因：今日 arXiv 清單無乾淨的計算加速頂會 accepted 論文 · Reviewer 資料：未抓取

TL;DR

把「模型怎麼寫」和「算子怎麼排程」拆開：用 torch.compile backend 讓 overlap / fusion / split 三類 intra-device 平行化，只改數十行就接進 vLLM、SGLang 等 6 個系統，吞吐最高 1.29×。

Abstract, p.1
問題

Intra-device parallelism 好用，卻幾乎沒人整合

  • 算子資源需求迥異：GEMM 是 compute-bound、decode attention / norm 是 memory-bound、AllReduce / all-to-all 是 network-bound，序列執行讓某資源總在閒置
  • SGLang 實作 dual-batch overlap：超過 2 個月、1.3K 行專用程式碼，且只針對一個模型
  • 框架（vLLM、SGLang）是靜態、循序的程式模型，與非循序執行衝突
瓶頸不是演算法，是整合成本。
§1, p.1–2
動機

資源閒置有多大？網路停滯最多讓 15% 效能留在桌上

§2, p.3
動機

沒有萬用策略：最佳選擇隨負載與硬體改變

  • Batch splitting 對大 batch（prefill）有利，小 batch 因多讀權重而變慢
  • A100：partial overlap（all-reduce + RMSNorm）優於 full overlap（SM 競爭）；H100：full overlap 較佳（multimem 指令卸載 reduction）
§1, p.2
背景

三類策略：overlap、fusion、split

§2.1, p.3–4
背景

三類策略各有整合痛點

策略做法痛點
OverlapCUDA streams / green contextsstream 有資源競爭；green context 需手調 SM 數；峰值記憶體上升
Fusion以專家寫的 custom kernel 取代多個算子算子子序列組合爆炸，難維護
Split沿 batch 維度切 micro-batch每多一份 micro-batch 多讀一次權重；何時切、切多細要決定；split/merge 的拷貝
§2.1, p.3–4
設計挑戰

三個要同時解決的問題

  1. 排程粒度：太細（torch.add 等）排程複雜、開銷高並阻礙 fusion；太粗（整層）暴露不出層內重疊
  2. 統一且動態的抽象：要夠表達各種策略，並能依 workload / 硬體 / 模型在執行期調整
  3. 效能不能因彈性而損失：控制流 / 資料流開銷、split/merge 拷貝、與 CUDA Graphs / TorchInductor 的靜態圖假設衝突

靜態編譯器（如 XLA）假設穩定的執行圖，難處理這種動態性（§2.2）。

§2.2, p.4
方法總覽

核心想法：在邏輯模型與實體執行之間插入可程式化的執行層

§3.1, p.4–5
方法 · 前端

Graph partition：沿用既有程式結構當排程單位

  • 輸入是 TorchDynamo 追蹤出的計算圖，故與 vLLM、SGLang 等已支援的系統相容
  • 排程目標通常是邏輯算子（RMSNorm、Attention），對應 nn.Module 或一次 PyTorch API 呼叫
  • API：SplitModule（依模組切）、SplitFunc（依函式呼叫切）、dynaflow.mark（任意程式區塊的 context manager）
用 2–3 種標註就能把細粒度圖收成粗粒度的可排程子圖。
§3.2.1, p.5
方法 · 前端

Programmable scheduling：三個原語組出任何排程

  • 使用者繼承 OpSchedulerBase、覆寫 schedule（Python-native）
  • split([bs1…bsn])：建立 n 個邏輯 micro-batch
  • get_ready_ops(i)：查詢第 i 個 micro-batch 依賴已滿足的子圖
  • execute(ops, stream, replace_func)：派發算子；多個 micro-batch 的同一算子可合併執行，或以 replace_func 換成 fused kernel；未特別指定時退回循序執行

設計取捨：直接暴露所有子圖會讓使用者自管資料流；宣告式改寫規則又不夠動態。

§3.2.2, p.5–6
方法 · 前端

範例：約 20 行 Python 寫出 DBO 與 TokenWeave

  • DBO：attention 以大 batch 執行、MoE 切兩個 micro-batch 重疊通訊與計算；執行期先判斷 batch size，不夠大就退回循序
  • TokenWeave：用 replace_func 把 AllReduce + RMSNorm 換成 fused kernel 並與下一個計算重疊
§3.2.2, p.6–7
方法 · 後端

零拷貝資料流：靜態分析 + 執行期預配置

  • 問題：micro-batch 數在上下游算子不同時需 re-shard，naive 的 torch.cat 拷貝會吃掉平行化收益
  • StaticAnalysis：每個 tensor 預先算 reference count（生命週期）與 prealloc 旗標（是否屬於未來的 merge）
  • RuntimeExecute：遞減 ref count 做垃圾回收；prealloc 的輸出先配一塊連續 buffer，hook 把算子輸出直接寫進對應切片
re-shard 變成零拷貝，記憶體生命週期也可追蹤。
§3.3.1, Algorithm 1, p.7
方法 · 後端

與 CUDA Graphs、TorchInductor 相容：靜態優化下放到子圖層級

  • TorchInductor：每個子圖只編譯一次，可跨 micro-batch 重用
  • CUDA Graphs：為避免並行資料衝突，對每個 micro-batch 與子圖各自 capture；並在同一 micro-batch 的所有子圖與 batch size 間共用 graph pool 以壓低記憶體
  • 實作：torch.compile backend，4.1K 行 Python，PyTorch 2.6+

§5.4, p.11
局限

作者自己點出的限制

  • Megatron-LM 訓練反向：custom fused TP backward 算子超出 TorchDynamo 有限的 compiled autograd 支援，overlap 效果差
  • 影片生成（Wan-14B）長序列由 attention 二次成長主導，通訊重疊收益下降
  • Megakernel 類技術的動態性（如 MoE 條件計算）仍是開放問題（Related Work）
  • 實驗僅在 B200 與 H100 NVLink 機器上；多節點低頻寬只在附錄以 PCIe 模擬
§5.3.3, §6, p.10–12
解讀

為什麼這個設計 work（我的解讀，非論文結論）

  • 把「策略」變成短小的 Python 函式，而不是散在框架各處的改寫——策略比較與實驗成本大降，Flux 的負結果也能快速驗出
  • 性能關鍵不在排程 API，而在後端：零拷貝 + CUDA Graph 相容讓彈性不被開銷吃掉（消融 0.96× → 1.14×）
  • 對工程師：想試新的 overlap 策略時，先確認 batch 條件與硬體，再決定是否開，比單一固定策略穩
